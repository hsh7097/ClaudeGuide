# 재귀 모드

> 재귀는 같은 판단을 반복하는 것이 아니라, 라운드마다 다른 검증 렌즈로 누락을 줄이는 절차다.

## 핵심 원칙

- 프롬프트 내용으로 작업 모드를 먼저 고른다.
- 라운드마다 같은 내용을 반복하지 말고 검증 관점을 바꾼다.
- 이전 라운드의 발견 사항, 수정 사항, 오탐 가능성을 다음 라운드에 누적한다.
- 마지막 라운드에서는 기존 발견이 실제 영향인지 다시 확인하고 중복 지적을 제거한다.
- 수정은 허용된 모드에서만 하고, 발견된 문제와 직접 연결되는 최소 변경만 한다.

## 모드 선택

### 1. 리뷰 재귀

사용 조건:
- "리뷰 재귀", "검토 재귀", "확인만", "수정하지 말고", "read-only"가 포함된 경우
- PR, diff, 코드 구조를 검토하되 사용자가 직접 수정 요청을 하지 않은 경우

규칙:
- 코드를 수정하지 않는다.
- 커밋, PR 댓글 등록, 파일 변경도 하지 않는다. 단, 사용자가 명시적으로 댓글 등록을 요청한 경우만 예외다.
- 각 라운드는 발견, 근거, 영향 범위, 오탐 가능성, 권장 코멘트만 누적한다.
- 마지막에는 BLOCK, WARN, QUESTION, NOTE로 나눠 보고한다.

### 2. 리뷰 수정 재귀

사용 조건:
- "리뷰 수정 재귀", "리뷰하고 수정까지", "검토 후 반영", "문제 있으면 고쳐줘"가 포함된 경우

규칙:
- 라운드 1은 먼저 read-only 리뷰로 문제를 확정한다.
- 확정된 문제만 최소 변경으로 수정한다.
- 라운드 2 이후는 수정된 코드가 새 문제를 만들었는지 다시 검증한다.
- 수정 후에는 가능한 빌드/테스트/정적 검사를 실행한다.

### 3. 개발 재귀

사용 조건:
- "개발 재귀", "구현 재귀", "작업해줘 재귀", "수정해줘 재귀"처럼 코드 변경이 명확한 경우

규칙:
- 라운드 1에서 최소 구현을 한다.
- 라운드 2는 리뷰어 관점으로 전체 변경 파일을 다시 읽고 문제만 수정한다.
- 라운드 3은 호출자, source set, 빌드/테스트, 경계값을 확인한다.
- 요청 밖 리팩토링은 하지 않는다.

### 4. 기본 재귀

사용자가 그냥 "재귀"만 붙인 경우:
- 요청이 리뷰/검토/PR 확인이면 리뷰 재귀로 실행한다.
- 요청이 구현/수정/반영이면 개발 재귀로 실행한다.
- 요청이 모호하고 수정 여부가 위험하면 한 문장으로 확인한다.

## 라운드별 검증 렌즈

각 라운드는 같은 검토를 반복하지 않는다. 아래 렌즈를 순서대로 적용한다.

### 라운드 1: 직접 변경점 렌즈

목표:
- 요청 의도와 실제 변경점이 맞는지 확인한다.
- diff, 변경 파일, 새 API, 삭제된 API, 직접적인 컴파일 위험을 본다.

확인 항목:
- 변경 목적이 코드에 반영됐는가
- 기존 동작이 바로 깨지는 부분은 없는가
- 삭제/변경된 시그니처의 직접 호출자가 남아 있는가
- 명확한 null, empty, boundary 문제가 있는가

### 라운드 2: 흐름/호출자 렌즈

목표:
- 변경 파일 전체를 다시 읽고 diff 밖의 영향까지 본다.
- 상태, 데이터, lifecycle, recomposition, side effect 흐름을 추적한다.

확인 항목:
- 호출자와 하위 컴포넌트의 책임 경계가 맞는가
- 상태 read/write 위치가 의도한 scope에 있는가
- 중복 구독, 중복 호출, 유실, race condition 가능성이 있는가
- preview, uiTest, flavor/source set 등 다른 진입점이 깨지지 않는가

### 라운드 3: 증거/회귀 렌즈

목표:
- 라운드 1-2 발견 사항이 실제 문제인지 재확인한다.
- 빌드, 테스트, 정적 검사, 검색 결과 같은 외부 증거로 마무리한다.

확인 항목:
- 이전 라운드의 지적이 오탐은 아닌가
- 수정한 부분이 새 문제를 만들지 않았는가
- 가능한 검증 명령이 통과했는가
- 남은 이슈는 BLOCK/WARN/QUESTION/NOTE 중 어디에 해당하는가

## 실행 절차

### 0. 히스토리 테이블 유지

매 라운드마다 아래 내용을 유지한다.

```text
| 라운드 | 렌즈 | 발견 | 조치 | 남은 리스크 |
|---|---|---|---|---|
| 1 | 직접 변경점 | | | |
| 2 | 흐름/호출자 | | | |
| 3 | 증거/회귀 | | | |
```

### 1. 라운드 실행

리뷰 재귀:
1. 대상 diff 또는 파일을 읽는다.
2. 라운드 렌즈에 맞게 발견 사항을 기록한다.
3. 수정하지 않고 근거와 영향 범위를 정리한다.
4. 이전 라운드 발견이 중복인지, 오탐인지, 더 강해졌는지 표시한다.

리뷰 수정 재귀:
1. 라운드 1에서 read-only로 문제를 확정한다.
2. 확정된 문제만 수정한다.
3. 수정한 파일 전체를 다시 읽는다.
4. 검증 명령을 실행하고 실패하면 같은 라운드에서 바로 수정한다.

개발 재귀:
1. 라운드 1에서 최소 구현한다.
2. 라운드 2에서 변경 파일 전체와 1-depth 호출자를 다시 읽는다.
3. 라운드 3에서 검증 명령과 source set/preview/test 영향을 확인한다.

### 2. 조기 종료

아래 조건이면 3라운드 전에도 종료할 수 있다.
- 라운드 2에서 신규 발견이 없고 검증 명령이 통과한 경우
- read-only 리뷰에서 라운드 2까지 동일 결론이고 추가 확인 가치가 낮은 경우
- 사용자의 시간/범위 제약상 추가 라운드가 비용 대비 효과가 낮은 경우

조기 종료 시에도 어떤 렌즈까지 봤는지 보고한다.

## 판정 기준

- BLOCK: 실제 컴파일 실패, 런타임 크래시, 데이터 유실, 명확한 회귀 가능성이 있는 문제
- WARN: 수정 권장. 운영 영향 가능성이 있으나 즉시 실패로 단정하기 어려운 문제
- QUESTION: 설계 의도 확인이 필요한 문제. 근거는 있으나 팀 판단이 필요한 경우
- NOTE: 참고 사항. 수정 강제는 아니다
- PASS: 마지막 라운드에서 신규 문제와 남은 수정 대상이 없다

## 금지 사항

- 리뷰 재귀에서 코드를 수정하지 않는다.
- 같은 지적을 라운드마다 반복하지 않는다.
- diff만 보고 최종 판단하지 않는다. 필요한 경우 전체 파일과 호출자를 다시 읽는다.
- "아마 괜찮다"로 끝내지 않는다. 근거, 영향 범위, 오탐 가능성을 분리한다.
- 확신이 낮은 지적을 BLOCK으로 올리지 않는다. QUESTION으로 분리한다.
- 요청 밖 리팩토링을 하지 않는다.
