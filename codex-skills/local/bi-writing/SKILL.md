# BI 작성 스킬

BI(BI-Weekly) 문서를 작성할 때 아래 기준을 따른다.

실제 초안을 쓸 때는 `references/examples.md`에서 현재 주제와 가장 가까운 예시 유형을 먼저 확인한 뒤, 그 톤과 밀도를 기준으로 작성한다.

## 1. BI의 목적

BI는 팀 내 기술 공유용 기록이다.

- 발표 자료가 아니다.
- 블로그 스타일의 장문 설명도 아니다.
- 나중에 다시 봤을 때 당시의 맥락, 문제, 판단, 결과를 빠르게 복원할 수 있어야 한다.

핵심은 "무엇을 했는지"보다 "왜 이걸 기록할 가치가 있었는지"가 드러나는 것이다.

## 2. 실제 작성 원칙

### 경험 중심

반드시 아래 중 대부분이 드러나야 한다.

- 어떤 작업/이슈 맥락이었는지
- 기존 방식이 왜 막혔는지
- 어떤 접근으로 풀었는지
- 적용 후 무엇이 달라졌는지

### 설명의 밀도

- 이론 설명만 길게 쓰지 않는다.
- 반대로 실제 문제 해결에 필요하면 클래스명, 메서드명, 처리 흐름, 검증 포인트는 적는다.
- "짧게 쓰는 것"보다 "나중에 다시 봐도 바로 이해되는 것"을 우선한다.

### 한 문서, 한 포인트

- 한 문서는 하나의 이슈, 개선, 실험, 디버깅 포인트를 중심으로 작성한다.
- 여러 주제를 한 문서에 섞지 않는다.

## 3. 분량 기준

기존처럼 무조건 5~8줄로 자르지 않는다. 실제 BI-Weekly 문서들은 더 넓은 범위를 가진다.

- 짧은 기록형: 5~8줄
- 일반 공유형: 8~20줄
- 상세 이슈 정리형: 15~40줄

판단 기준:

- 단순 팁/도구 소개면 짧게
- 장애 원인, 구조 변경, 재현/검증 포인트가 있으면 길게
- 코드 변경 이유와 검증 기준이 중요하면 구조화해서 길게

## 4. 제목 규칙

제목은 문제/행동/결과가 바로 보이게 작성한다.

좋은 예:

- 홈 백그라운드 진입 시 Paging 네트워크/파싱 중단 처리
- Android 6 WebView 키보드 미노출 이슈
- ViewHolder 내에서 Impression 보내는 시점

피해야 할 예:

- 안드로이드 관련 정리
- 이번에 한 작업
- 페이징 공부

## 5. 기본 구조

기본적으로는 아래 흐름을 따른다.

1. 배경
2. 문제
3. 대응
4. 결과

다만 실제 주제 난이도에 따라 아래 두 가지 작성 모드를 쓴다.

### A. 짧은 기록형

도구 사용 팁, UI 이슈, 디버깅 포인트, 간단한 개선에 사용한다.

권장 흐름:

- 어떤 상황에서 필요했는지
- 기존에 뭐가 불편했는지
- 어떤 방법을 썼는지
- 적용 후 무엇이 가능해졌는지

### B. 구조화된 상세형

장애 대응, 구조 개선, 비동기 흐름, 성능/페이징/상태관리/아키텍처 이슈처럼 맥락이 중요한 경우 사용한다.

권장 섹션:

- 개요
- 배경
- 문제 또는 기존 한계
- 최종 처리 방향
- 상세 변경 내용
- 기대 효과 또는 결과
- 검증 포인트
- 필요 시 적용 파일 / 참고 링크 / 첨부 이미지

모든 섹션을 강제로 쓰지는 않는다. 주제에 필요한 만큼만 쓴다.

## 6. 무엇을 포함할지

포함해도 좋은 것:

- 실제 이슈가 난 조건
- 실패했던 접근
- 최종 채택한 방식
- 클래스명 / 메서드명 / API명
- 검증 방법
- 스크린샷, 로그, 첨부 이미지 링크

과하게 넣지 말아야 할 것:

- 불필요한 이론 설명
- 교과서식 정의
- 실제 판단과 무관한 배경지식
- 코드 전체 복붙

코드는 원칙적으로 설명용으로만 최소 포함한다.

## 7. 문체 가이드

선호:

- ~ 이슈가 있었다
- ~ 상황에서 문제가 발생했다
- 기존에는 ~ 한계가 있었다
- 이번에는 ~ 방식으로 정리했다
- 이 처리로 ~ 가 가능해졌다

비선호:

- 공식 문서에 따르면
- 내부적으로 ~ 구조이기 때문에
- 일반적으로 ~ 해야 한다

설명보다 맥락과 판단을 우선한다.

## 8. 출력 규칙

- 문장은 짧고 단정하게 쓴다.
- 불릿/번호/짧은 문단을 섞어도 된다.
- 필요할 때만 섹션 헤더를 쓴다.
- 문서 마지막에 첨부 이미지 섹션을 둘 수 있다.
- 과장, 홍보성 표현, 불필요한 미사여구는 쓰지 않는다.

## 9. 작성 판단 기준

문서를 쓰기 전에 아래를 먼저 판단한다.

1. 이 주제가 짧은 기록형인지, 구조화된 상세형인지
2. 나중에 다시 볼 때 꼭 남아야 할 판단/처리/검증 포인트가 무엇인지
3. 독자가 "왜 이걸 공유했는지"를 첫 몇 줄 안에 이해할 수 있는지

## 10. 예시 방향
실제 예시는 `references/examples.md`를 참고한다.

초안 생성 시 규칙:

- 도구/디버깅 팁이면 "짧은 기록형" 예시를 따른다.
- 테스트 방법/운영 가이드면 "실행 가이드형" 예시를 따른다.
- 구조 변경/장애 대응이면 "구조화된 상세형" 예시를 따른다.
- 최근에 다뤘던 이슈를 BI로 써달라는 요청이면, 대화 내용 중 문제-대응-결과를 추출한 뒤 가장 가까운 예시 구조로 바로 초안을 만든다.

## 11. 핵심 요약

BI는 "짧게 잘 쓴 문서"가 아니라 "맥락과 판단이 남는 기록"이다.

주제가 단순하면 짧게 쓰고, 주제가 복잡하면 구조화해서 쓴다.
