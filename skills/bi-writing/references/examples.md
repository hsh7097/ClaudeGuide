# BI 예시 모음

아래 예시는 실제 BI-Weekly 문서 패턴을 기준으로 정리한 샘플이다.

초안을 쓸 때는 주제와 가장 가까운 패턴 하나를 골라 밀도와 구조를 맞춘다.

---

## 1. 짧은 기록형

사용 상황:

- 디버깅 팁
- 특정 도구 사용법
- 단일 UI 이슈
- 빠르게 공유할 가치가 있는 작업 메모

예시:

SFC 작업 중 WebView 내부를 앱 화면만으로 확인하기 어려운 경우가 있었다.

특히 페이지 자체 이슈인지 앱 브리지 이슈인지 구분이 안 되는 경우가 많았다.

확인 방법을 찾던 중 `chrome://inspect/#devices` 를 사용해 Android WebView를 직접 디버깅할 수 있었다.

이 방법을 적용하면 실행 중인 WebView와 내부 HTML 구조를 바로 확인할 수 있어 원인 파악이 훨씬 빨라졌다.

포인트:

- 문단 4~6개 정도로 짧게 끝낸다.
- 원인보다 "언제 썼고 뭐가 좋아졌는지"를 우선한다.

---

## 2. 실행 가이드형

사용 상황:

- 테스트 방법 정리
- 운영/개발 환경별 호출 방법
- 재현 절차 공유

예시:

리얼타임 팝콘은 FCM을 통해 내려오기 때문에 테스트 방법 문의가 자주 발생했다.

현재 구조상 dev와 운영에서만 테스트가 가능하다.

테스트는 아래 순서로 진행한다.

1. 계정 로그인 후 `custNo`를 확인한다.
2. 환경별 전송 URL에 접속한다.
3. `memberId`에 `custNo`, `popcornSeq`에 팝콘 시퀀스를 넣어 호출한다.

이 문서는 테스트 흐름을 빠르게 다시 확인할 수 있도록 남긴다.

포인트:

- 절차가 핵심이면 번호 목록을 허용한다.
- 설명보다 재현/실행 단계가 우선이다.

## 3. 구조화된 상세형

사용 상황:

- 구조 변경
- 백그라운드/비동기/페이징 이슈
- 장애 대응
- 검증 포인트가 중요한 개선

예시:

## 개요

홈 Content Paging load 중 앱이 background로 내려가면 네트워크 요청과 JSON 파싱이 끝까지 수행될 수 있는 이슈가 있었다.

## 배경

기존 구조에서는 load가 진행 중인 상태에서 앱이 background로 전환되어도 일부 작업이 그대로 계속 실행됐다.

초기에는 load 자체를 cancel하는 방식도 검토했지만, 이 경우 Paging 에러 상태가 정상 반영되지 않아 resume 후 retry가 어려웠다.

## 최종 처리 방향

최종적으로는 load 본체는 유지하고 fetch/parse 작업만 child job으로 분리해 background 시점에 취소하도록 정리했다.

이렇게 하면 background에서는 불필요한 작업을 멈추고, resume 후에는 기존 retry 흐름을 유지할 수 있다.

## 검증 포인트

- fetch 진행 중 background 진입 시 에러 상태가 정상 반영되는지
- parse 진행 중 중단되는지
- resume 후 retry가 가능한지

포인트:

- 섹션을 써도 된다.
- 처리 배경, 선택 이유, 검증 기준이 같이 남아야 한다.

## 4. UI 정리형

사용 상황:

- 다수 화면/컴포넌트 조정
- before/after 성격의 스타일 정리
- 접근성, dp/sp, 반응형 대응

예시:

홈 영역에서 `sp`가 잘못 들어가 있거나 레이아웃이 깨져 보이는 부분이 있어 정리를 진행했다.

이번 작업은 디자인 일치보다도, 실제 기기에서 잘리거나 겹치는 영역을 안정화하는 데 목적이 있었다.

주요 변경은 다음과 같다.

- 타이틀/숏컷/버튼 텍스트 `dp` 기준 정리
- 가격 영역 반응형 처리
- 고정 높이로 잘리던 영역을 wrap/flex 기준으로 수정

이 문서는 세부 화면별 수정 목록을 다시 확인하기 위한 기록이다.

포인트:

- 항목 나열이 필요하면 불릿을 써도 된다.
- "왜 이 정리가 필요했는지"를 첫 문단에 먼저 쓴다.
