# 재귀 모드

> 한 번에 완벽할 수 없다. 같은 사이클을 3번 돌려야 수렴한다.

## 핵심 개념

**재귀 = 전체 작업 사이클을 3회 반복**

```
라운드 1: 실행 → 검증 → 수정 대상 확인
라운드 2: 수정 실행 → 검증 (라운드1 히스토리 포함) → 수정 대상 확인
라운드 3: 수정 실행 → 최종 검증 (라운드1+2 히스토리 포함) → 완료
```

매 라운드는 이전 라운드의 **히스토리를 누적**하여 검증한다.
라운드가 진행될수록 검증 범위가 넓어지고 깊어진다.

---

## 작업 유형별 사이클

### A. 개발 + 재귀 (예: "이거 개발해줘 재귀")

```
[라운드 1]
  개발 → 검증 → 개발 영역 확인 → 수정 체크

[라운드 2]
  수정 개발 → 검증 → 개발 영역 확인 → 수정 체크

[라운드 3]
  수정 개발 → 최종 검증 → 개발 영역 확인 → 완료
```

각 라운드의 **검증** 단계:
1. 변경된 파일을 **전체 다시 Read**로 읽는다 (diff만 보지 않음)
2. 구체적 시나리오 최소 3개로 데이터 흐름 추적
3. 유실/중복/사이드이펙트 확인
4. 동시성/메모리/경계값 확인
5. 문제 발견 시 → 수정 대상으로 기록 → 다음 라운드에서 수정

### B. 검증 + 재귀 (예: "이거 확인해줘 재귀")

```
[라운드 1]
  검증 → 수정 영역 확인 → 수정 적용

[라운드 2]
  추가 검증 (라운드1 히스토리 포함) → 수정 영역 확인 → 수정 적용

[라운드 3]
  최종 검증 (라운드1+2 히스토리 포함) → 수정 영역 확인 → 완료
```

각 라운드의 **검증** 단계:
1. 대상 파일/문서를 **전체 다시 Read**로 읽는다
2. 실제 코드/데이터와 교차 검증
3. 이전 라운드에서 수정한 부분이 새로운 문제를 만들지 않았는지 확인
4. 문제 발견 시 → 즉시 수정 → 수정 이력에 추가

---

## 실행 절차

### 0. 히스토리 테이블 초기화

매 라운드 시작 전 아래 테이블을 유지한다:

```
| 라운드 | 발견 사항 | 수정 내용 | 검증 결과 |
|:-----:|----------|----------|:--------:|
| 1     |          |          |          |
| 2     |          |          |          |
| 3     |          |          |          |
```

### 1. 라운드 N 실행

**실행** (개발 작업인 경우):
- 라운드 1: 최초 개발/작업 수행
- 라운드 2+: 이전 라운드에서 발견된 수정 대상을 반영

**검증**:
1. 변경된 **모든 파일을 Read로 다시 읽는다** (diff만 보지 않음)
2. 구체적 시나리오로 한 줄씩 추적 (추상적 "아마 괜찮겠지" 금지)
3. 검증 관점:
   - **데이터 흐름**: 입력→처리→출력이 정상인가?
   - **유실/중복**: 데이터가 조용히 사라지거나 2번 처리되는 경로는?
   - **동시성/메모리**: race condition, 무한 성장 컬렉션, Context 릭?
   - **경계값**: null, empty, 0, 빈 문자열?
   - **사이드이펙트**: 기존 코드에 영향을 주는가?

**수정 대상 확인**:
- 발견된 문제를 히스토리 테이블에 기록
- 수정이 필요하면 즉시 적용 (다음 라운드가 아닌 **현재 라운드에서**)
- 수정 후 해당 부분만 재검증

### 2. 라운드 간 히스토리 누적

라운드 2는 라운드 1의 발견/수정 이력을 **참조하며** 검증한다.
라운드 3은 라운드 1+2의 이력을 **모두 참조하며** 검증한다.

중요: 이전 라운드에서 수정한 부분이 **새로운 문제를 만들지 않았는지** 반드시 확인.

### 3. 종료 조건

- 3라운드 모두 완료
- 또는 라운드 N에서 수정 대상이 0건이면 조기 종료 가능

## 최종 보고

```
🔄 재귀 완료 ({N}/3 라운드)

[라운드 1]
- 발견: {내용}
- 수정: {내용 또는 "없음"}

[라운드 2]
- 발견: {내용} (라운드1 수정분 포함 검증)
- 수정: {내용 또는 "없음"}

[라운드 3]
- 발견: {내용} (라운드1+2 수정분 포함 검증)
- 수정: {내용 또는 "없음"}

[누적 수정 이력]
1. {수정1}
2. {수정2}
...

최종 판정: {PASS / WARN / BLOCK}
```

판정 기준:
- **PASS**: 마지막 라운드에서 수정 대상 0건
- **WARN**: 경미한 이슈 남았으나 운영에 영향 없음
- **BLOCK**: 해결되지 않은 문제 존재 → 추가 작업 필요

---

## 하지 않는 것

- ❌ diff만 보고 판단 (반드시 전체 파일을 Read로 읽는다)
- ❌ "아마 괜찮을 것" 판단
- ❌ 리뷰 중 코드 스타일/포맷팅 지적
- ❌ 요청 외 리팩토링 제안
- ❌ 추상적 시나리오 — 반드시 구체적 값으로 추적
- ❌ 라운드 간 히스토리 무시 — 이전 라운드 결과를 반드시 참조
